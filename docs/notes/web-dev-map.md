# 0. 이 문서를 읽는 법

**순서대로 읽어야 한다.** 뒤 장이 앞 장의 *대가*에서 나오기 때문이다.

```text
React 의 대가       → 매 프레임 화면에 안 맞다   → Phaser 가 필요해진다
Next.js 의 대가     → 서버가 끼어든다           → "window 가 없다" 가 생긴다
Phaser 의 대가      → 1.3MB                   → 번들을 쪼개게 된다
```

기술마다 아래 다섯 칸으로 쓴다.

```text
그 전에는 이렇게 했다     없던 시절을 먼저 본다
뭐가 불편했나            여기가 핵심. 불편이 곧 존재 이유다
발상                    그래서 뭘 뒤집었나
대가                    공짜인 기술은 없다. 여기서 다음 기술이 나온다
이 프로젝트에서는         우리 코드 어디
> 이렇게 설명하면 된다     서너 줄. 소리 내어 말할 수 있게
```

1장은 배경이라 이 틀을 쓰지 않는다.

```text
1  웹이 뭘로 굴러가나
2  왜 React 가 생겼나

5  Tailwind 와 Phaser 의 자리
6  개발이 굴러가는 한 바퀴  ★
7  이 프로젝트를 지도 위에 올리기
```

# 1. 웹이 뭘로 굴러가나

## 브라우저는 무슨 프로그램인가

한 문장으로 — **받아온 텍스트를 화면으로 만드는 프로그램**이다.

주소창에 `example.com` 을 치면 이런 일이 벌어진다.

```text
1  주소로 상대 컴퓨터를 찾는다
2  "이 페이지 좀 줘" 하고 요청한다
3  HTML 텍스트 한 덩어리를 받는다        ← 이 시점엔 그냥 글자다
4  브라우저가 읽으면서 DOM 나무를 만든다
5  CSS 를 입혀서 실제로 그린다
6  <script> 를 만나면 자바스크립트를 실행한다
7  그 자바스크립트가 DOM 을 고치면 화면이 다시 그려진다
```

**3번에서 받는 것이 글자 뭉치일 뿐**이라는 게 중요하다. 3장에서 "빈 껍데기를
보내면 카카오톡이 못 읽는다"는 얘기가 나오는데, 그게 이 3번 얘기다.

## DOM — 문서를 나무로 만든 것

4번에서 만드는 나무가 **DOM**(Document Object Model)이다.

```text
html
 └ body
    ├ h1        "장바구니"
    └ div
       ├ span   "3개"
       └ button "결제"
```

자바스크립트가 화면을 바꾼다는 건 **이 나무의 가지를 고친다**는 뜻이다.
브라우저는 나무가 바뀌면 그 부분을 다시 그린다.

**HTML 은 종이, DOM 은 그걸 읽고 머릿속에 세운 구조**라고 보면 된다.
HTML 은 처음 한 번 읽히고 끝이지만 DOM 은 계속 살아 있으면서 바뀐다.

## 셋의 역할 분담

```text
HTML   뭐가 있나        구조와 내용
CSS    어떻게 보이나     색 · 크기 · 배치
JS     무슨 일이 나나    누르면 · 바뀌면 · 시간이 지나면
```

건물로 치면 골조 · 마감 · 전기설비다. 골조 없이 마감을 할 수 없고,
전기설비는 나중에 들어와서 이미 있는 것을 움직인다.

## "서버"는 뭘 하는 물건인가

특별한 기계 이름이 아니다. **요청이 오면 뭔가를 돌려주는 역할**의 이름이다.
하는 일은 크게 둘로 갈린다.

```text
정적   가지고 있던 파일을 그대로 준다
       사진 · HTML · CSS 파일. 누가 요청하든 같은 것
동적   요청을 받고 나서 계산해서 만들어 준다
       로그인한 사람 이름 · 방금 올라온 댓글. 사람마다 다름
```

**이 프로젝트는 정적만 한다.** 방명록을 넣는 순간 처음으로 동적이 필요해진다.
이 갈림이 나중에 배포 방식을 통째로 정한다.

그리고 서버는 남의 컴퓨터일 필요가 없다.

```powershell
npm run dev   # 이 순간 내 노트북이 서버 역할을 한다
```

`localhost:3000` 의 `localhost` 가 **"나 자신"** 이라는 뜻이다.
내 노트북이 요청을 받고 내 노트북이 답한다. 그래서 노트북을 끄면 안 열린다.
배포란 결국 **이 역할을 24시간 켜져 있는 남의 컴퓨터에게 넘기는 일**이다.

## 이 프로젝트에서는

여기서 좀 이상하게 느껴질 수 있는데, 짚고 가자.

```text
HTML   직접 쓴 적이 거의 없다     JSX 가 대신한다 (2장)
CSS    파일을 거의 안 만들었다    Tailwind 가 대신한다 (5장)
JS     직접 쓴 적이 없다         TypeScript 로 쓰고 변환된다 (4장)
```

**셋 다 여전히 있다.** 다만 직접 쓰지 않고 도구가 만들어낸다. 결국 브라우저에
도착하는 건 HTML · CSS · JS 셋뿐이다. 앞으로 나올 기술들은 전부
**이 셋을 더 편하게 만들어내는 방법**이다.

그리고 이 프로젝트에는 특이한 게 하나 있다. 마을 화면 전체가 DOM 이 아니라
**`<canvas>` 태그 하나**다. 그 안은 DOM 이 아니라 그림이라, 브라우저
개발자 도구로 열어봐도 캐릭터가 안 보인다. 왜 그렇게 했는지는 2장 끝에 나온다.

# 2. 왜 React 가 생겼나

## 그 전에는 이렇게 했다

DOM 의 가지를 손으로 찾아서 고쳤다.

```js
// 장바구니에 물건이 하나 늘었다
document.getElementById('count').textContent = '3';
document.getElementById('total').textContent = '45,000원';
document.getElementById('empty-msg').style.display = 'none';
document.getElementById('checkout-btn').disabled = false;
```

## 뭐가 불편했나

데이터는 **한 곳**에서 바뀌었는데 화면은 **네 군데**를 따로 고쳐야 한다.
하나를 빠뜨리면 "장바구니가 비었습니다" 라고 쓰여 있는데 결제 버튼은 켜져 있는
화면이 된다.

기능이 늘수록 고칠 자리가 곱셈으로 는다. 그리고 **어긋나도 에러가 안 난다.**
그냥 이상한 화면이 보일 뿐이다. 이게 제일 나쁘다. 에러는 잡을 수 있지만
이건 사람이 눈으로 봐야 안다.

## 발상

> 화면을 고치지 말고, **데이터로부터 화면을 다시 만들자.**

```jsx
function Cart({ items }) {
  if (items.length === 0) return <p>장바구니가 비었습니다</p>;
  return (
    <div>
      {items.length}개 · {total(items)}원
      <button>결제</button>
    </div>
  );
}
```

`items` 하나만 바꾸면 화면이 그 값에 맞게 통째로 다시 만들어진다.
**어긋날 자리가 없다.** 데이터가 진짜고 화면은 그 결과일 뿐이니까.

여기서 용어 네 개가 나온다.

```text
컴포넌트   화면 한 조각을 만드는 함수. 위의 Cart
JSX       함수 안에 HTML 처럼 생긴 걸 쓰는 문법. 브라우저는 모른다 (3장)
props     컴포넌트가 밖에서 받는 값. 위의 items
상태      컴포넌트가 스스로 들고 있는 값. 이게 바뀌면 다시 그려진다
```

"전부 다시 만들면 느리지 않나" — 그래서 React 는 새로 만든 결과를 이전 것과
비교해서 **실제로 달라진 가지만** 진짜 DOM 에 반영한다. 이 비교 대상이 되는
가벼운 사본을 가상 DOM 이라 부른다.

## 대가

```text
매번 다시 만들고 비교하는 비용이 든다
→ 1초에 60번 바뀌는 화면에는 안 맞는다
```

움직이는 화면은 사실 **정지 그림을 빠르게 갈아 끼우는 것**이다. 그 한 장 한 장을
**프레임**(frame)이라고 한다. 만화영화와 똑같다.

부드럽게 보이려면 1초에 60장이 필요하고, 그러면 한 장에 쓸 수 있는 시간이
**16.7밀리초**밖에 없다 (1초 ÷ 60). 그 안에 "다시 만들고 · 비교하고 · DOM 고치고 ·
브라우저가 다시 그리고"를 전부 넣기는 어렵다.

캐릭터가 걸어다니는 화면은 매 프레임 바뀐다. **여기서 게임 엔진이 필요해진다.**
5장으로 이어진다.

## 이 프로젝트에서는

```text
components/   전부 React    모달 · 대화창 · 결혼식 정보 · 시작 화면
              가끔 바뀐다. 열리고 닫힌다. React 가 잘하는 일
game/         전부 Phaser   맵 · 캐릭터 · 카메라
              매 프레임 바뀐다. React 가 못하는 일
```

1장 끝에서 말한 `<canvas>` 태그 하나가 이거다.
**React 는 캔버스가 거기 있다는 것만 알고, 그 안에서 무슨 일이 벌어지는지 모른다.**

둘이 만나는 지점은 파일 하나뿐이다 — `components/game/GameCanvas.tsx`.

> **이렇게 설명하면 된다**
> "DOM 을 직접 고치면 데이터와 화면이 따로 놀아서 어긋납니다. React 는 상태에서
> 화면을 다시 만드는 방식이라 그 어긋남이 구조적으로 생기지 않습니다.
> 대신 매번 다시 만들고 비교하는 비용이 있어서, 매 프레임 갱신되는 게임 화면은
> Phaser 에 맡기고 UI 만 React 로 그렸습니다."

# 3. 왜 Next.js 를 또 얹나

## 그 전에는 이렇게 했다

React 만 쓰면 화면 조각은 만들 수 있는데 **그 바깥이 전부 비어 있다.**
크게 셋이다.

```text
빌드        브라우저는 JSX 를 모른다. 누가 변환해서 묶어줘야 한다
라우팅      주소마다 다른 화면. React 에는 그 개념이 아예 없다
서버 렌더링  첫 HTML 을 누가 만들어 보내나
```

## 뭐가 불편했나 ① — 빌드

브라우저는 `<div>{items.length}개</div>` 같은 걸 이해하지 못한다.
**JSX 는 자바스크립트가 아니다.** 누군가 이걸 평범한 자바스크립트로 바꿔줘야 한다.

파일 수백 개를 그대로 보내는 것도 문제다. 요청 한 번에 파일 하나씩이라 수백 번을
주고받게 된다. 그래서 몇 덩어리로 **묶는다**(번들). 쓰지 않는 코드는 빼고,
공백과 변수 이름도 줄인다.

옛날에는 이 변환기와 묶는 도구를 각각 골라서 설정 파일을 손으로 엮었다.
그것만으로 며칠이 갔다.

## 뭐가 불편했나 ② — 라우팅

`/` 와 `/about` 에 다른 화면을 보여주는 것. 너무 당연해 보이지만
**React 에는 그 기능이 없다.** React 는 "화면 한 조각을 만드는 방법"이지
"주소를 다루는 방법"이 아니다.

## 뭐가 불편했나 ③ — 서버 렌더링 ★

이게 이 프로젝트에서 **결정적**이었다.

React 만 쓰면 서버가 보내는 HTML 이 이렇게 생겼다.

```html
<body>
  <div id="root"></div>          <!-- 비어 있다 -->
  <script src="bundle.js"></script>
</body>
```

브라우저가 `bundle.js` 를 받아 실행해야 그제서야 내용이 채워진다.
사람이 볼 때는 문제없다. 잠깐 하얗다가 뜬다.

**문제는 사람이 아닌 것이 읽을 때다.**

**크롤러**(crawler)는 사람 대신 웹페이지를 돌아다니며 내용을 긁어가는
프로그램이다. *crawl* 이 "기어다니다"라서 붙은 이름이다. 검색엔진이 세상의
페이지를 훑는 것도, 카카오톡이 링크 미리보기를 만드는 것도 이것이다.

```text
카카오톡 · 검색엔진 크롤러
  → HTML 만 받아서 훑고 간다. 자바스크립트를 실행하지 않는다
  → 위 HTML 을 받으면 "빈 페이지" 로 본다
```

청첩장은 **링크로 전달되는 서비스**다. 카톡에 링크를 붙였을 때 뜨는 미리보기
카드가 사실상 첫인상이다. 그게 안 뜨면 서비스가 반쯤 실패한다.
그래서 **서버가 만든 HTML 안에 정보가 이미 들어 있어야** 했다.

## 발상

> 이 셋을 매번 엮지 말고, **정답을 정해서 한 덩어리로 주자.**

```text
빌드        설정 없이 된다. JSX · TypeScript · 번들 · 최적화 전부
라우팅      폴더 구조가 곧 주소다. app/page.tsx → "/"
서버 렌더링  기본값이다. 끄는 게 아니라 켜는 걸 안 해도 된다
```

## 언제 HTML 을 만드느냐 — 세 가지

여기서 약자 셋이 나온다. 차이는 딱 하나, **HTML 을 만드는 시점**이다.

```text
CSR   빈 HTML 을 보내고 브라우저가 만든다        재료만 주고 손님이 조리
SSR   요청이 올 때마다 서버가 만든다             주문 받고 조리
SSG   빌드할 때 미리 만들어 파일로 둔다           미리 만들어 진열
```

```text
        첫 화면    서버 필요    사람마다 다른 내용
CSR     느림       없어도 됨    가능
SSR     빠름       필요함       가능
SSG     제일 빠름   없어도 됨    불가능
```

**이 프로젝트는 SSG 다.** 청첩장은 누가 보든 내용이 같으니 미리 만들어두면 된다.
서버가 아예 필요 없어지고, 그래서 배포가 파일 올리는 일로 끝난다.

```ts
// next.config.ts
output: "export"    // 빌드하면 out/ 에 완성된 파일이 나온다
```

방명록을 넣으면 이 줄을 지워야 한다. 사람마다 다른 내용이 생기니까.

## 대가

**서버가 끼어든다.** 그래서 내 코드가 두 곳에서 실행된다.

```text
1  빌드할 때 (Node.js 위)   → 여기엔 window 도 document 도 없다
2  브라우저에서             → 여기엔 있다
```

Phaser 는 `window` 를 당연히 있는 것으로 보고 시작한다. 그래서 그냥 불러오면
**빌드 도중에 터진다.**

여기서 흔한 오해가 하나 있다.

> `'use client'` 를 붙였으니 브라우저에서만 도는 것 아닌가?

**아니다.** 그건 "브라우저에서도 돈다"는 표시지 "서버에서 안 돈다"가 아니다.
첫 HTML 을 만들기 위해 **서버에서 한 번은 실행된다.**
이 오해가 이 프로젝트에서 실제로 시간을 잡아먹었다.

해결은 `useEffect` 안에서 동적으로 불러오는 것이다.
`useEffect` 는 브라우저에서만 돌기 때문이다.

```tsx
useEffect(() => {
  (async () => {
    const Phaser = await import("phaser");   // 이 시점엔 브라우저다
    // ...
  })();
}, []);
```

또 하나의 대가는 **정답이 정해져 있다**는 것이다. 편한 만큼 벗어나기 어렵고,
버전이 오르면 규칙이 바뀐다. 이 프로젝트도 Next.js 16 을 쓰는데
인터넷 예제 상당수가 안 맞는다.

## 이 프로젝트에서는

```text
app/page.tsx                   주소 "/" 하나뿐. 라우팅 덕은 크게 못 봤다
app/layout.tsx                 모든 페이지를 감싸는 껍데기 · 메타 태그
app/opengraph-image.tsx        카톡 미리보기 이미지를 코드로 그린다  ← ③ 의 답
next.config.ts                 output: "export" → SSG
components/game/GameCanvas.tsx useEffect 안에서 Phaser 를 불러온다  ← 대가의 대응
```

**메타 태그**(meta tag)는 화면에 보이지 않는 정보를 기계에게 알려주는 HTML
태그다. 페이지 제목 · 설명 · 미리보기 이미지 주소 같은 것. 사람은 그림과 글을
보지만 크롤러는 이걸 본다.

**셋 중 라우팅은 거의 안 썼고, 서버 렌더링 하나 때문에 골랐다.**
이런 건 솔직하게 말하는 게 낫다.

> **이렇게 설명하면 된다**
> "청첩장은 링크로 전달되니까 카카오톡 미리보기가 첫인상입니다. 크롤러는
> 자바스크립트를 실행하지 않아서, 서버가 만든 HTML 안에 메타 정보가 이미
> 들어 있어야 했습니다. 그래서 Next.js 를 썼습니다.
> 내용이 사람마다 같아서 정적 생성으로 뽑았고, 덕분에 서버 없이 배포됩니다.
> 대신 빌드 때 서버 환경에서도 코드가 한 번 돌기 때문에, window 를 쓰는
> Phaser 는 useEffect 안에서 동적으로 불러오도록 분리했습니다."

# 4. TypeScript 가 더하는 것

## 그 전에는 이렇게 했다

자바스크립트는 값에 **종류가 없다.**

```js
function walkTo(x, y) { /* ... */ }

walkTo(15, 26);        // 됨
walkTo("15", 26);      // 이것도 그냥 실행된다
walkTo(15);            // 이것도 실행된다. y 는 undefined
```

문제가 있어도 **그 줄이 실제로 실행될 때까지 아무도 모른다.**

## 뭐가 불편했나

두 가지인데, 뒤엣것이 훨씬 나쁘다.

```text
① 실행해봐야 안다
   화면 다섯 번 눌러서 들어가는 자리면 다섯 번 눌러야 알 수 있다

② 안 터지고 조용히 틀린다
   "15" + 1 은 에러가 아니라 "151" 이다
   undefined 로 계산하면 NaN 이 되고, 그대로 화면에 반영된다
```

그리고 셋째. **함수가 뭘 받는지 알 수가 없다.** 남이 쓴 코드든 두 달 전의 내
코드든 열어서 읽어봐야 한다.

## 발상

> 값에 **이름표를 붙이고, 실행하기 전에 검사하자.**

```ts
function walkTo(x: number, y: number) { /* ... */ }

walkTo("15", 26);   // 저장하는 순간 에디터가 빨간 줄을 긋는다
```

여기서 헷갈리기 쉬운 게 하나 있다. **타입은 실행되는 코드가 아니다.**

```text
내가 쓴 것      const x: number = 5
브라우저가 받는 것  const x = 5          ← 타입은 사라진다
```

빌드할 때 검사만 하고 지워진다. 실행 속도에는 영향이 없고, 반대로
**실행 중에 들어오는 값은 못 막는다.** 서버에서 받아온 데이터가 예상과 다르면
타입은 아무것도 해주지 않는다. 어디까지나 **내가 쓴 코드끼리의 약속**이다.

## 이 프로젝트에서 특히 값을 한 이유

### 좌표계가 세 개다

전부 `number` 인데 의미가 다른 값이 섞여 있다.

```text
타일 좌표   (15, 26)      맵에서 몇 번째 칸인가
픽셀 좌표   (248, 424)    게임 세계 안의 위치
화면 좌표   (180, 320)    카메라(3배 확대)를 거친 뒤 화면 위 위치
```

섞으면 **에러 없이 조용히 캐릭터가 엉뚱한 데로 간다.** 위의 ② 그대로다.
제일 찾기 어려운 종류의 버그다.

그래서 타입을 만들고 변환을 함수로만 하게 했다.

```ts
// game/maps/pathfinding.ts
export type TilePoint = { x: number; y: number };
```

```text
tileToPixelCenter(15, 26)    타일 → 픽셀
pixelToTile(248, 424)        픽셀 → 타일
camera.getWorldPoint(...)    화면 → 픽셀
```

### 경계의 계약

React 와 Phaser 사이에 오가는 건 문자열 id 뿐이다(2장 끝). 타입이 없으면
어느 쪽이 무엇을 보내는지 **문서를 봐야만 안다.**

```ts
// types/index.ts
export type WorldObjectKind = "frame" | "villager" | "venue" | "signpost";
```

이렇게 **정해둔 값 중 하나만** 올 수 있게 하는 타입을 **유니온 타입**이라고 한다.
"이거 아니면 저거"를 세로줄(`|`)로 늘어놓는다는 뜻이다.

이렇게 해두면 새 종류를 추가할 때 **처리를 빠뜨린 자리를 검사기가 잡아준다.**
실제로 표지판을 추가할 때 그랬다. `signpost` 를 목록에 넣자마자,
네 종류를 나눠 처리하던 자리에서 "signpost 는 어떻게 할 거냐" 고 빨간 줄이 떴다.

## 대가

```text
쓰는 속도가 느려진다        특히 처음에
남의 라이브러리 타입이 방대하다  Phaser 타입에서 한참 헤맸다
런타임은 못 지킨다          실행 중 들어오는 값은 별개 문제
```

> **이렇게 설명하면 된다**
> "자바스크립트는 잘못된 값이 들어와도 실행되기 때문에, 에러가 안 나고 조용히
> 틀리는 경우가 제일 위험합니다. 이 프로젝트는 타일·픽셀·화면 좌표가 전부
> number 라서 섞여도 티가 안 났고, 타입과 변환 함수로 그 경계를 고정했습니다.
> React 와 Phaser 사이 계약도 유니온 타입으로 두니 종류를 추가할 때
> 처리 누락을 컴파일 단계에서 잡을 수 있었습니다."

# 5. Tailwind 와 Phaser 의 자리

앞의 셋과 달리 이 둘은 **없어도 굴러간다.** 편해서 쓴 것이라 대가도 더 작다.

## 5-1. Tailwind — CSS 파일을 안 만드는 방식

### 그 전에는 이렇게 했다

CSS 를 따로 파일에 쓰고, 이름을 지어서 연결했다.

```css
.memory-modal-header { display: flex; align-items: center; gap: 8px; }
```
```html
<div class="memory-modal-header">
```

### 뭐가 불편했나

```text
이름 짓기가 일이다            .card-title-wrapper-inner 같은 게 생긴다
어디서 쓰이는지 모른다         이 클래스 지워도 되나? 무서워서 못 지운다
안 쓰는 CSS 가 쌓인다         지우면 어디가 깨질지 모르니 계속 남는다
```

### 발상

> 이름을 짓지 말고, **미리 만들어둔 작은 클래스를 조합하자.**

```html
<div class="flex items-center gap-2">
```

`flex` 는 `display: flex` 하나, `gap-2` 는 `gap: 8px` 하나. 이렇게
**한 가지 일만 하는 작은 클래스**를 **유틸리티**(utility)라고 부른다.
공구함에 든 드라이버 하나하나에 가깝다. 조합해서 쓰라고 만든 것이다.

이름이 없으니 **지울 때 이 줄만 보면 된다.** 다른 데 영향이 없다.

### 대가

HTML 이 길어지고 처음엔 지저분해 보인다. 그리고 이 프로젝트에서 실제로
한 번 물렸다.

**캐스케이드 레이어**(cascade layer)는 CSS 규칙에 **층을 매기는 기능**이다.
원래 CSS 는 같은 자리를 두고 규칙이 겹치면 **더 구체적으로 지목한 쪽**이 이긴다.
이것을 명시도라고 한다. `#id` 가 `.class` 를 이기는 식이다.

레이어가 있으면 **명시도를 보기 전에 층부터 본다.**

```text
층 밖의 규칙        ← 무조건 위. 아무리 뭉뚝해도 이긴다
층 안의 규칙        ← 아무리 구체적이어도 진다
```

Tailwind 유틸리티는 층 안에 들어간다. 그래서 `globals.css` 에 무심코 쓴
평범한 `body { }` 한 줄이 층 밖에 있는 바람에 **모든 Tailwind 클래스를
이겨버렸다.** `!important` 로 덮을 뻔했는데, 원인이 명시도가 아니라 층이라
덮어봐야 다음에 또 물린다. 층을 맞추는 게 답이었다.

### 이 프로젝트에서는

UI 가 적어서 이득이 컸다. 모달 몇 개와 정보창이 전부라
**CSS 파일을 따로 만들 만큼이 아니었다.** `app/globals.css` 는 거의 비어 있다.

## 5-2. Phaser — 게임 엔진이 대신 해주는 것

### 그 전에는 이렇게 했다

`<canvas>` 에 브라우저가 주는 그리기 명령을 직접 쓴다.

```js
ctx.drawImage(playerImage, x, y);
```

그림 한 장 그리는 건 이걸로 된다. 문제는 그 바깥이다.

### 뭐가 불편했나

게임이라면 뭘 만들든 **똑같이 필요한 것들**이 있다.

```text
루프        1초 60번 다시 그리기 · 기기가 느려도 속도가 같게
스프라이트   그림 한 장을 여러 칸으로 잘라 번갈아 보여주기
충돌        겹쳤는지 매 프레임 검사하고 밀어내기
카메라      세계는 큰데 화면은 작다. 어디를 비출지
타일맵      작은 그림을 격자로 반복해 큰 맵 만들기
입력        키보드 · 터치를 좌표로
```

이걸 매번 다시 만든다. **게임 만들기 전에 게임 만드는 도구부터 만들게 된다.**

### 발상

> 그 공통을 전부 들고 있는 틀을 쓰고, **화면 단위로 나눠 담자.**

그 화면 단위가 **Scene** 이다. 이 프로젝트는 둘로 나눴다.

```text
BootScene    그림(텍스처)을 준비한다. 준비되면 다음으로 넘긴다
WorldScene   마을. 맵 · 플레이어 · 오브젝트 · 조작 · 카메라
```

**텍스처**(texture)는 **게임이 화면에 그릴 그림 데이터**다. 그림 파일을 읽어
그래픽카드가 바로 쓸 수 있는 형태로 올려둔 것을 말한다. 요리 전에 재료를
손질해 접시에 담아두는 것과 비슷하다 — 그리는 순간에 파일을 여는 게 아니라
미리 준비해 둔다.

BootScene 을 따로 둔 이유가 이것이다. 이 프로젝트는 그림 파일 대신
**코드로 그려서** 텍스처를 만든다.

### 대가

```text
무겁다        압축해도 1.3MB. 모바일 청첩장에서 가볍지 않다
버전 차이     이 프로젝트는 4.x 인데 인터넷 예제 대부분이 3.x 다
```

무게는 실제 문제였고, 그래서 **시작 화면에서 [입장하기] 를 눌러야 받도록**
쪼갰다. 첫 화면 173KB, 게임 진입 후 352KB.

**gzip 기준**이라고 쓰는데, gzip 은 파일을 보낼 때 **압축해서 보내고 브라우저가
받아서 푸는** 방식이다. 코드는 같은 단어가 반복돼서 잘 줄어든다. 그래서
디스크에 있는 크기가 아니라 **실제로 네트워크를 타는 크기**를 말할 때 이 기준을 쓴다.

**React 의 대가가 Phaser 를 불렀고, Phaser 의 대가가 번들 분리를 불렀다.**
0장에서 말한 사슬이 이거다.

### 이 프로젝트에서는

```text
game/scenes/       BootScene · WorldScene
game/maps/         맵 데이터 · 오브젝트 배치 · 길찾기
game/objects/      길잡이 고양이 · 나비
game/textures/     코드로 그린 임시 그래픽
```

## 다섯이 한 화면에서 어떻게 겹쳐 있나

```text
브라우저
 └ HTML 문서 (DOM)
    │
    ├ React 가 만든 부분          모달 · 대화창 · 결혼식 정보 · 시작 화면
    │    └ 생김새는 Tailwind 클래스
    │
    └ <canvas> 태그 하나           ← 여기부터는 DOM 이 아니다
         └ Phaser 가 그린다        맵 · 캐릭터 · 카메라 · 고양이

 전부 TypeScript 로 쓰고
 Next.js 가 변환 · 묶음 · HTML 생성 · 정적 내보내기를 맡는다
```

```text
Next.js      바깥 틀           빌드 · 라우팅 · HTML 만들기
React        가끔 바뀌는 화면    DOM
Tailwind     그 화면의 생김새
Phaser       매 프레임 바뀌는 화면  Canvas
TypeScript   위 전부를 쓰는 언어
```

> **이렇게 설명하면 된다**
> "성격이 다른 두 렌더링을 한 화면에 올렸습니다. 가끔 바뀌는 UI 는 React 로
> DOM 에 그리고, 매 프레임 바뀌는 게임 화면은 Phaser 가 캔버스 하나 안에
> 그립니다. 둘은 서로를 모르고 접점은 파일 하나입니다.
> Phaser 는 1.3MB 라 초기 로딩에 부담이라, 시작 화면에서 입장할 때 받도록
> 분리해서 첫 화면을 173KB 로 맞췄습니다."

# 6. 개발이 굴러가는 한 바퀴

앞의 다섯 장이 "무엇을 쓰는가"였다면 이 장은 **"어떻게 굴리는가"** 다.

## 배경 — 왜 단계가 이렇게 많은가

옛날에는 이랬다.

```text
1  라이브러리 홈페이지에서 파일을 내려받는다
2  프로젝트 폴더에 넣는다
3  HTML 에 <script src="jquery-1.9.js"> 라고 적는다
4  끝. 브라우저가 바로 읽는다
```

단순했다. 문제는 둘이었다.

```text
버전이 꼬인다      A 는 라이브러리 1.9 를 원하고 B 는 2.1 을 원한다
                  누가 뭘 쓰는지 아무도 모른다. 올렸다가 어디가 깨질지 모른다
브라우저가 못 읽는다  JSX · TypeScript · Tailwind 는 브라우저가 모르는 문법이다
                  누가 평범한 HTML · CSS · JS 로 바꿔줘야 한다
```

**첫째를 푸는 것이 npm, 둘째를 푸는 것이 빌드다.** 아래 단계들은 전부 이
둘에서 나왔다.

## 한 바퀴 전체

```text
npm install        도구와 라이브러리를 내려받는다        처음 한 번
   ↓
npm run dev        개발 서버를 켠다                    작업하는 내내 켜둔다
   ↓  ←──────┐
브라우저 확인      눈으로 본다                          고치면 즉시 반영
   ↓         │
코드 수정 ────┘
   ↓
tsc · lint         실행 안 해보고 잡아낸다
   ↓
npm run build      진짜 결과물을 만든다                 out/ 에 파일이 떨어진다
   ↓
git commit · push  기록하고 올린다                      → 자동 배포
```

## 1. npm install — 도구를 내려받는다

### npm 이 뭔가

**npm**(Node Package Manager)은 **남이 만든 코드를 대신 받아다 주고 버전을
관리해주는 프로그램**이다. 앱스토어에 가깝다. 이름만 적으면 알아서 받아온다.

여기서 **패키지**(package)는 남이 만들어 공개해둔 코드 묶음, **의존성**
(dependency)은 "내 프로젝트가 돌아가려면 필요한 것"이라는 뜻이다.

### 파일 두 개가 짝을 이룬다

```text
package.json        내가 원하는 것.        "next 16 이상"
package-lock.json   실제로 받은 것.        "next 16.0.3 정확히 이것"
```

**설계도와 준공 도면**의 차이다. 설계도에는 "창문 크기 100 이상"이라고 적혀
있지만, 실제로 지은 건물엔 정확히 몇 짜리가 들어갔는지 준공 도면에 남는다.
lock 파일이 있어서 **다른 컴퓨터에서도 똑같은 버전이 깔린다.**

### node_modules — 실제로 받아온 것들

```text
package.json 에 적힌 것        11개
node_modules 안의 폴더         292개
node_modules 전체 용량         575 MB
```

**의존성이 또 의존성을 갖기 때문**이다. Next.js 가 다른 걸 쓰고, 그게 또
다른 걸 쓴다. 그래서 열한 개를 적었는데 이백구십두 개가 들어온다.

이 폴더는 **git 에 올리지 않는다.** 용량이 크고, `package-lock.json` 만 있으면
언제든 똑같이 다시 만들 수 있기 때문이다. 다른 컴퓨터에서 `npm install` 한 번
치면 되는 이유가 이것이다.

### 실무 — 여기서 겪은 것

**엉뚱한 폴더에서 설치한 적이 있다.** `node_modules/next/` 안에서 명령을 쳐서
거기에 또 설치가 됐다. npm 은 현재 폴더를 기준으로 동작하니까 조용히 성공한다.

```powershell
pwd    # 명령 치기 전에 위치부터 확인한다
```

복구 방법과 자세한 내용은 [../SETUP.md](../SETUP.md).

## 2. npm run dev — 개발 서버

### 세 가지를 동시에 한다

```text
변환   TypeScript · JSX · Tailwind 를 브라우저가 아는 것으로 바꾼다
서빙   그 결과를 localhost:3000 으로 내보낸다
감시   파일이 바뀌는지 계속 지켜본다
```

1장에서 말한 대로, 이때 **내 노트북이 서버 역할**을 한다.

### 고치면 바로 반영되는 원리

파일을 저장하면 화면이 새로고침 없이 바뀐다. 이걸 **핫 리로드**(hot reload)
또는 HMR 이라고 한다.

원리는 이렇다. 개발 서버와 브라우저가 **연결을 계속 열어둔다.** 파일이 바뀌면
서버가 그 조각만 만들어서 열린 통로로 밀어 넣고, 브라우저는 **바뀐 부분만
갈아 끼운다.**

**공연 중에 무대 세트 한 조각만 바꾸는 것**과 같다. 막을 내리고 다시 올릴
필요가 없다.

**다만 이 비유가 안 맞는 지점이 있다.** 세트를 바꿔도 배우가 서 있던 자리는
그대로인 것처럼, **화면의 상태는 남아 있다.** 그래서 코드는 고쳤는데 화면이
이상한 상태로 남는 경우가 생긴다.

이 프로젝트에서 실제로 당했다. **이미 고친 문제의 옛날 에러가 화면에 계속
떠 있어서** 엉뚱한 곳을 진단했다. 이럴 땐 새로고침하거나 서버를 껐다 켠다.

## 3. 브라우저에서 확인 — 개발자 도구

`F12` 로 여는 창이다. 네 곳만 알면 된다.

```text
Elements    지금 화면의 DOM 나무. 어떤 태그에 어떤 CSS 가 먹었는지
Console     로그와 에러. 빨간 글씨가 뜨면 여기부터 본다
Network     브라우저가 무엇을 몇 KB 받았는지. 번들 크기를 재는 곳
Application 저장된 데이터 · 캐시
```

**이 프로젝트는 특이한 점이 있다.** 마을 화면은 `<canvas>` 하나라
Elements 에서 열어봐도 **캐릭터도 액자도 안 보인다.** 그냥 태그 하나다
(1장 · 2장). 그 안은 DOM 이 아니라 그림이라서, 게임 쪽 문제는 개발자 도구가
아니라 로그와 코드로 잡아야 한다.

## 4. tsc · lint — 실행하지 않고 잡아낸다

```powershell
npx tsc --noEmit   # 타입 검사만. 파일은 만들지 않는다
npm run lint       # 문법은 맞지만 문제 될 코드를 잡는다
```

### 왜 따로 돌리나

**변환기는 타입을 검사하지 않는다.** TypeScript 를 자바스크립트로 바꿀 때
타입 표시를 **지우기만** 한다(4장). 빠르려고 그렇게 만들어져 있다.

그래서 타입이 틀려도 개발 서버는 잘 돌아간다. 검사는 `tsc` 를 따로 불러야 한다.

`--noEmit` 은 **"결과 파일을 만들지 마라"** 는 뜻이다. 검사만 하고 끝낸다.

### 실행 안 해보고 잡는다는 게 왜 중요한가

화면 다섯 번 눌러야 들어가는 자리의 버그는, 실행해서 찾으려면 **매번 다섯 번
눌러야 한다.** 검사는 그걸 안 누르고 찾는다.

## 5. npm run build — 진짜 결과물

### 개발 서버와 뭐가 다른가

```text
개발 서버   빠른 게 최우선. 필요한 것만 그때그때 변환. 결과는 메모리에만
빌드       느려도 좋다. 전부 변환하고, 줄이고, 미리 계산해서 파일로 떨군다
```

빌드가 더 하는 일들 —

```text
쓰지 않는 코드를 뺀다
공백과 변수 이름을 줄인다
파일을 몇 덩어리로 묶는다 (번들)
HTML 을 미리 만들어 둔다 (SSG · 3장)
```

### out/ 에 뭐가 생기나

```text
out/
  index.html            미리 만들어진 HTML. 열면 내용이 이미 들어 있다
  404.html
  opengraph-image        카톡 미리보기 PNG
  _headers               Cloudflare 에 줄 지시서
  favicon.ico
  memories/ wedding/     사진과 약도
  _next/static/          변환된 JS · CSS 덩어리들
```

**이게 전부다.** 서버 프로그램이 없다. 그냥 파일 뭉치다(3장 SSG).

용량을 비교해보면 빌드가 무슨 일을 하는지 한눈에 보인다.

```text
node_modules/   575 MB     만들 때 필요한 도구와 재료
out/              2.2 MB   실제로 하객 폰에 가는 것
```

**575MB 중에 2.2MB 만 나간다.** 나머지는 전부 만드는 데만 쓰이고 버려진다.
공장에 기계가 가득해도 트럭에 실리는 건 완제품뿐인 것과 같다.

### 파일 이름이 왜 `2gdu25e1vgz0_.js` 인가

이름에 붙은 무작위 글자를 **해시**라고 한다. 내용이 바뀌면 이 글자도 바뀐다.

**캐시** 때문이다. 브라우저는 한 번 받은 파일을 저장해뒀다가 다음엔 안 받는다.
빠르지만 문제가 있다 — **파일 이름이 같으면 내용이 바뀐 걸 모른다.**

```text
이름이 고정   app.js       내용이 바뀌어도 옛날 걸 계속 쓴다
해시가 붙음   app-a1b2.js  내용이 바뀌면 app-c3d4.js 가 되어 새로 받는다
```

**이름을 바꿔서 강제로 새로 받게 하는 것**이다. 그래서 안 바뀐 파일은 계속
캐시를 쓰고, 바뀐 것만 새로 받는다.

## 6. 배포 — 그 파일들이 어디로 가나

`out/` 을 24시간 켜져 있는 컴퓨터에 올려두는 것이 전부다(1장). 절차는
[../DEPLOY.md](../DEPLOY.md), 자동으로 도는 구조는
[ai-workflow.md](ai-workflow.md).

## 7. git 은 이 사이클 어디에 끼나

**어디에도 안 낀다.** 사이클과 나란히 돈다.

```text
사이클    고치고 → 확인하고 → 검사하고 → 빌드하고
git      그 과정 어디서든 "지금 이 상태를 저장" 할 수 있다
```

git 은 **되돌아갈 지점을 만드는 일**이지 만드는 일의 일부가 아니다. 다만 이
프로젝트에서는 `git push` 가 배포 방아쇠라(6번), **push 만은 사이클의 끝에
붙는다.**

## 실무 — 이 프로젝트에서 실제로 치는 명령

```powershell
npm install        # 처음 한 번, 또는 다른 컴퓨터에서 받았을 때
npm run dev        # 작업하는 내내 켜둔다
npx tsc --noEmit   # 고친 뒤
npm run lint
npm run build      # 여기까지 통과해야 올린다
```

```text
AI 가 하는 것    tsc · lint · build 를 통과시키는 것까지
사람이 하는 것    브라우저와 폰에서 눈으로 확인
```

> **이렇게 설명하면 된다**
> "npm 이 의존성을 버전 고정해서 받아오고, 개발 중에는 dev 서버가 변환과
> 핫 리로드를 맡습니다. 변환기는 타입을 지우기만 하니까 tsc 는 따로 돌려서
> 검사하고요. 빌드에서 번들링과 정적 생성이 일어나 out 폴더에 결과가 떨어지는데,
> 파일명에 콘텐츠 해시가 붙어서 캐시 무효화가 자동으로 됩니다.
> 이 프로젝트는 push 가 배포 트리거라 push 시점이 곧 릴리스 시점입니다."

# 7. 이 프로젝트를 지도 위에 올리기

여기까지가 지도다. 이제 **우리가 실제로 만든 순서**를 그 위에 얹는다.
"이 개념 언제 쓴 거지" 가 풀리는 자리다.

## 만든 순서와 밟은 자리

```text
①  프로젝트 만들기            6장    npm · 폴더 구조 · 명령 네 개
②  캔버스 띄우기              3장    서버에는 window 가 없다 (Next.js 의 대가)
                             2장    React 는 캔버스가 있다는 것만 안다
③  마을 그리기                5장    Phaser · 타일맵 · 텍스처
④  캐릭터 움직이기             5장    게임 루프 · 프레임 · 충돌 · 카메라
                             4장    좌표계 세 개
⑤  누르면 열린다              2장    React 와 Phaser 의 경계
                             4장    유니온 타입으로 계약을 고정
⑥  탭하면 걸어간다             4장    화면 좌표 → 픽셀 → 타일 변환
                             지도 밖  A* 길찾기
⑦  길을 잃는다 → 고양이        지도 밖  기술이 아니라 사용자 판단
⑧  폰에서 무너진다             1장    CSS · DOM · 화면 높이
                             5장    Tailwind 의 캐스케이드 레이어
⑨  카톡 미리보기               3장    서버가 만든 HTML 에 메타 태그
                             1장    크롤러는 JS 를 실행하지 않는다
⑩  번들 쪼개기                5장    Phaser 의 1.3MB
                             6장    빌드 · 번들 · 해시
⑪  배포                      1장    서버란 무엇인가
                             3장    SSG — 서버가 아예 필요 없어진다
                             6장    build → out/ → 올리기
```

**⑦ 만 지도 밖에 있다.** 기술로 푼 게 아니라 "하객의 절반이 어르신"이라는
판단으로 풀었기 때문이다. 그리고 면접에서 제일 잘 먹히는 것도 보통 이런
쪽이다. 기술은 배우면 되지만 판단은 겪어야 나온다.

## 무엇이 무엇을 불렀나

0장에서 예고한 사슬이다. 이제 전부 이어진다.

```text
매 프레임 바뀌는 화면이 필요하다
  → React 로는 안 된다 (다시 만들고 비교하는 비용)      2장
  → Phaser 를 쓴다                                  5장
  → 1.3MB 다                                        5장
  → 시작 화면에서 나눠 받는다                          6장 · 11장

링크로 전달되는 서비스다
  → 크롤러가 읽을 HTML 이 필요하다                     1장 · 3장
  → Next.js 를 쓴다                                 3장
  → 서버가 끼어든다. window 가 없다                    3장
  → useEffect 안에서 동적으로 불러온다                  2장 · 3장

누가 봐도 내용이 같다
  → 미리 만들어두면 된다 (SSG)                        3장
  → 서버가 필요 없다                                 1장
  → 파일만 올리면 배포 끝                             6장
```

**한 줄로 줄이면** — 청첩장이라 링크가 첫인상이고, 게임이라 매 프레임 그려야
하고, 내용이 고정이라 서버가 필요 없다. 이 세 가지가 스택 전부를 결정했다.

## 아직 지도에 안 밟은 칸

1장에서 서버가 하는 일을 둘로 나눴다.

```text
정적   가지고 있던 파일을 그대로 준다        ← 지금까지 전부 여기
동적   요청을 받고 계산해서 만들어 준다        ← 아직 안 해봤다
```

**방명록이 이 칸이다.** 하객이 글을 남기면 사람마다 화면이 달라지니
미리 만들어둘 수 없다. 그러면 이런 것들이 줄줄이 딸려 온다.

```text
next.config.ts 의 output: "export" 를 지운다      3장이 뒤집힌다
글을 어디에 저장하나                              데이터베이스
누가 썼는지 · 이상한 글을 어떻게 막나                검증 · 스팸 대응
```

**지금 이 프로젝트가 전부 프론트엔드인 이유**가 여기 있고, 다음에 할 일도
여기다.
