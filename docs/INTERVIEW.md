# 2. 왜 React만으로는 안 되는가

## 원리 — DOM과 Canvas는 그리는 방식이 다르다

**DOM**은 브라우저가 관리하는 **요소들의 트리**다. 요소 하나를 움직이면
브라우저는 이런 일을 한다.

```text
스타일 계산  →  레이아웃(어디에 얼마 크기로 놓일지)  →  페인트  →  합성
```

문제는 **레이아웃**이다. 요소 하나가 움직이면 형제와 부모의 위치도 다시
계산해야 할 수 있다. 이걸 리플로우(reflow)라고 한다.

**Canvas**는 요소가 하나다. 그 안은 그냥 **픽셀 배열**이다.
레이아웃 엔진이 개입하지 않는다. 지우고 다시 칠할 뿐이다.

## 왜 이게 문제가 되는가 — 16.7밀리초

부드러운 화면은 초당 60프레임이다. **한 프레임에 쓸 수 있는 시간이 16.7ms**다.

캐릭터·나비 7마리·고양이·오브젝트가 매 프레임 움직이는데 이걸 전부 DOM으로
하면 매 프레임 수십 번의 레이아웃 계산이 일어난다. 16.7ms를 넘기면 프레임이
밀리고 화면이 끊긴다.

```text
React  =  가끔 바뀌는 화면을 DOM으로 그린다   (버튼, 모달, 폼)
Phaser =  매 프레임 바뀌는 화면을 Canvas에 직접 그린다
```

## 이 프로젝트에서는

역할을 나눴다.

```text
Phaser  맵 · 캐릭터 · 이동 · 충돌 · 카메라 · 오브젝트
React   모달 · 결혼식 정보 · 대화창 · 시작 화면
```

# 3. 왜 게임인데 Next.js를 쓰는가

## 원리 — 카카오톡 미리보기는 자바스크립트를 실행하지 않는다

링크를 카톡에 붙이면 카카오 서버가 그 주소를 **직접 방문해서 HTML을 읽는다.**
그리고 `<meta property="og:title">` 같은 태그를 찾아 카드를 만든다.

여기서 중요한 것은 **크롤러는 자바스크립트를 실행하지 않는다**는 점이다.
React가 브라우저에서 나중에 태그를 넣어봐야 소용없다.
**서버가 보내주는 최초 HTML 안에 이미 들어 있어야 한다.**

## 왜 이게 중요한가

청첩장은 카톡으로 전달된다. **하객이 보는 첫 화면은 마을이 아니라 링크 카드다.**
공들여 만든 픽셀 마을이 있어도 그걸 열기 전에 카드부터 본다.

## 이 프로젝트에서는

`app/opengraph-image.tsx`에서 **1200x630 미리보기 이미지를 코드로 생성**했다.
그림 파일을 따로 관리하지 않고, 결혼식 데이터 파일을 고치면 이미지도 같이 바뀐다.

# 4. 핵심 소재 ① — React와 Phaser의 경계 설계

**가장 자신 있게 말할 부분이다. 시간을 여기 쓴다.**

## 문제

두 시스템이 서로를 알기 시작하면 코드가 엉킨다.
게임이 모달 생김새를 알거나, React가 캐릭터 좌표를 알면 끝이다.

## 해결 — 단방향 신호, id만 던진다

```text
WorldScene.interactWith()
      ↓  game.events.emit(GAME_EVENT.OPEN_MEMORY, "memory-jeju")
GameCanvas (React)
      ↓  findMemory("memory-jeju") → setState
MemoryModal (DOM)
```

**Scene은 무엇을 보여줄지 모른다.** "이 id를 열어달라"고 알릴 뿐이다.

덕분에 모달 디자인을 통째로 바꿔도 게임 코드는 한 줄도 안 건드린다.
접점은 `components/game/GameCanvas.tsx` 파일 하나뿐이다.

이벤트 이름은 상수로 뒀다. 문자열을 직접 쓰면 오타가 나도
**아무 일도 일어나지 않고 조용히 실패**한다. 이게 제일 찾기 어렵다.

---

## 4-1. 서버에는 window가 없다

### 원리 — 서버 렌더링이 실제로 하는 일

Next.js는 요청이 오면 **서버에서 React 컴포넌트를 실행해 HTML 문자열을 만든다.**
그걸 먼저 보내서 화면이 빨리 뜨게 하고, 크롤러도 읽을 수 있게 한다.
그다음 자바스크립트가 도착하면 React가 그 HTML에 이벤트를 붙인다(하이드레이션).

**서버에서 실행될 때는 브라우저가 없다.** `window`도 `document`도 없다.
Node.js 프로세스일 뿐이다.

Phaser는 모듈을 읽는 순간 `window`를 참조한다. 그래서 터진다.

### `'use client'`에 대한 흔한 오해

`'use client'`는 **"서버에서 실행하지 마라"가 아니다.**
"이 컴포넌트는 브라우저에서도 동작해야 하니 자바스크립트를 같이 보내라"는 뜻이다.

**초기 HTML을 만들기 위해 서버에서 한 번은 실행된다.**
그래서 `'use client'`를 붙여도 파일 상단 import는 여전히 서버에서 실행된다.

### 해결 — useEffect 안에서 동적 import

```text
파일 상단 import      → 서버에서도 실행됨      ✗
useEffect 안 import   → 브라우저에서만 실행됨   ✓
```

**왜 useEffect는 안전한가** — React의 effect는 컴포넌트가 **실제 DOM에 붙은 뒤**
실행된다. 서버에는 실제 DOM이 없으니 effect는 아예 실행되지 않는다.

**동적 import가 하는 일** — `await import()`는 그 줄에 도달했을 때 비로소
모듈을 불러온다. 번들러도 이걸 알아서 별도 파일로 쪼갠다.
그래서 그 모듈의 최상단 코드(Phaser가 window를 만지는 부분)가
그 시점까지 실행되지 않는다.

> 타입만 쓰는 `import type`은 컴파일하면 사라지므로 상단에 둬도 안전하다.

---

## 4-2. 정리하지 않으면 캔버스가 두 개 생긴다

### 원리 — React는 개발 모드에서 일부러 두 번 실행한다

React 18부터 개발 모드는 컴포넌트를 **마운트 → 언마운트 → 다시 마운트**한다.

일부러 그런다. 앞으로 React가 상태를 보존한 채 컴포넌트를 떼었다 붙이는
기능을 준비 중인데, 그때 **정리 코드가 없는 컴포넌트는 망가지기 때문**이다.
지금 미리 드러내주는 것이다.

### 이 프로젝트에서 실제로 일어난 일

정리 코드가 없으면 첫 번째 게임이 계속 돌면서 캔버스가 화면에 남고,
두 번째 게임이 또 생긴다. **캔버스가 두 개**가 된다.

```text
useEffect(() => {
  game = createGame(container);
  return () => game.destroy(true);   // ← 이게 없으면 두 개
}, []);
```

### 여기에 비동기가 겹치면

```text
① 컴포넌트 등장 → import 시작
② 사용자가 즉시 이동 → cleanup 실행
③ import 완료 → 게임 생성 ...정리해 줄 사람이 없음
```

`cancelled` 플래그로 ③을 막았다. **비동기 작업은 완료 시점에
"내가 아직 유효한가"를 확인해야 한다**는 일반적인 패턴이다.

# 5. 핵심 소재 ② — 알고리즘을 필요해서 썼다

## 5-1. A* 길찾기

### 왜 필요했나

화면을 탭하면 그 자리로 걸어가게 만들었다.
직선으로 가면 나무나 연못에 걸려 벽에 붙은 채 제자리걸음을 한다.

### 원리 — 다익스트라에 "감"을 더한 것

먼저 **너비 우선 탐색(BFS)**을 생각해보자. 출발점에서 사방으로 한 칸씩
물결처럼 퍼져나간다. 목적지에 닿으면 끝이다. 정확하지만 **목적지 반대편까지
똑같이 퍼진다.** 낭비가 크다.

**A\***는 여기에 한 가지를 더한다. 다음에 살펴볼 칸을 고를 때
이 값이 가장 작은 칸부터 본다.

```text
지금까지 온 비용  +  목적지까지 남은 거리의 어림값
```

뒤쪽 어림값 때문에 **목적지 방향으로 먼저 뻗어나간다.** 그래서 빠르다.

### 어림값을 아무렇게나 정하면 안 된다

어림값이 **실제 거리보다 크면 안 된다.** 크게 잡으면 진짜 최단 경로를
"멀어 보인다"고 건너뛰어 버린다.

4방향만 움직이는 격자에서는 **맨해튼 거리**(가로 차이 + 세로 차이)가
정확히 이 조건을 만족한다. 벽이 없으면 딱 그만큼이고, 벽이 있으면 그보다 멀다.
절대 실제보다 크지 않다. 그래서 최단 경로가 보장된다.

### 왜 대각선을 뺐나

4방향만 허용하면 **벽 모서리를 비스듬히 통과하는 문제**를 신경 쓰지 않아도 된다.
대각선을 허용하면 나무 두 그루 사이의 대각선 틈으로 몸이 빠져나간다.
결과 경로가 타일 격자에 자연스럽게 맞는 이점도 있다.

### 왜 우선순위 큐를 안 썼나

맵이 32×48 = **1,536칸**이다. 매번 선형으로 훑어도 충분히 빠르다.
**필요 없는 최적화를 하지 않았다.**

> 맵이 수만 칸이 되면 그때 힙을 넣으면 된다고 답하면 된다.

### 끼임 대비

물리 충돌로 모서리에 낄 수 있다. **1.5초 동안 진전이 없으면 자동 이동을 포기**한다.
알고리즘이 옳아도 물리 엔진과 만나면 예외가 생긴다.

---

## 5-2. 고양이는 길찾기를 쓰지 않는다

플레이어를 따라다니는 고양이가 있다. 여기에 A*를 쓰면
**매 프레임 경로를 다시 계산**해야 한다. 목표가 계속 움직이니까.

대신 **플레이어가 지나온 자리를 기록해 그 자취를 밟게 했다.**

```text
플레이어가 3px 움직일 때마다 위치를 기록 → 최대 10개 유지
고양이는 가장 오래된 기록을 향해 걷는다
```

**왜 안전한가** — 플레이어가 실제로 지나간 곳이다. 벽일 리가 없다.
길찾기가 아예 필요 없다.

길찾기는 **자취를 벗어나 새 목적지로 안내할 때만** 쓴다.

> 같은 문제라도 상황에 따라 훨씬 값싼 해법이 있다는 예로 쓸 수 있다.

---

## 5-3. 데이터 검증을 자동화했다

### 무슨 일이 있었나

맵을 눈으로 보고 만들었는데, **울타리로 완전히 막힌 칸이 8개** 있었다.
탐험이 목적인 서비스에서 못 가는 공간은 곤란하다.

### 어떻게 찾았나 — BFS

여기서는 **최단 거리가 필요 없다.** "닿을 수 있느냐"만 알면 된다.
그럴 때는 A*가 아니라 BFS다. 출발점에서 물결처럼 퍼뜨려
**끝까지 퍼진 칸의 개수**를 세면 된다.

```text
걸을 수 있는 칸 1,152개  vs  실제로 도달한 칸 1,144개  →  8칸이 고립
```

### 오브젝트 배치도 같은 방식으로

- 오브젝트가 놓인 칸이 걸을 수 있는 칸인가
- 인접 칸 중에 도달 가능한 곳이 있는가 (오브젝트 자체가 벽이므로)
- 참조하는 데이터 id가 실제로 존재하는가
- 오브젝트끼리 같은 칸에 겹치지 않는가

> **눈으로 검수하지 않고 검증을 자동화했다**는 점을 강조한다.

# 6. 핵심 소재 ③ — 기술이 아니라 사용자를 근거로 결정했다

**3년차에게 흔하지 않은 소재다. 여기가 차별점이다.**

## 배경

청첩장은 하객의 절반이 어르신이다. 게임 문법에 익숙한 사람에게 자연스러운 것이
어르신에게는 피로가 된다.

그래서 판단 기준을 문서로 못박았다.

```text
좋음   가만히 있어도 알려준다     움직이는 오브젝트, 먼저 말 거는 NPC, 길잡이 동물
나쁨   알아내야 알 수 있다        "이게 표지판이구나" 하고 눌러봐야 하는 것
```

**부담의 정체는 "해석"이다.** 표지판은 네 단계를 요구한다.
저게 표지판임을 알아보고, 누를 수 있다고 짐작하고, 누르고, 읽는다.

## 만든 것을 지운 사례 — 화면 방향 버튼

상하좌우 버튼을 만들었다가 실제 폰에서 보고 지웠다.

- 버튼 하나가 최소 56px, 십자 배치면 화면 아래 4분의 1을 먹는다
- 대화창이 뜨는 자리와 겹친다
- 무엇보다 **"이건 게임이다, 조작을 배워야 한다"는 신호**를 준다

대신 탭하면 그 자리로 걸어가는 방식만 남겼다.
**지금 화면에는 조작용 UI가 하나도 없다.**

## UI를 늘리지 않고 문제를 푼 사례 — 길잡이 고양이

카메라를 3배로 당기니 캐릭터는 잘 보이는데 **화면에 맵의 5%만 들어와**
길을 잃기 쉬워졌다.

후보는 화살표, 미니맵, 전체 지도 버튼이었다. **전부 화면에 UI를 더한다.**

대신 고양이를 한 마리 풀었다. 평소에는 따라다니고,
2초쯤 가만히 있으면 아직 안 본 곳으로 몇 걸음 앞서가서 돌아본다.

> 화면에 아무것도 늘리지 않고 길 안내를 해결했다.
> 그리고 **안내 장치는 하나만 둔다**는 원칙도 세웠다.
> 셋을 같이 두면 사용자가 뭘 봐야 할지 몰라 오히려 헷갈린다.

## 설명 대신 보여준 사례

"화면을 눌러 이동하세요"라는 문장 대신,
입장 직후 **손가락이 나타나 한 번 톡 누르고 사라지면 캐릭터가 그리로 걸어간다.**
딱 한 번만.

글을 읽게 하는 것보다 3초 시연이 빠르다.

## 전달성 안전장치

탐험이 즐거워도 정보가 안 닿으면 청첩장으로서 실패다.
시작 화면에 **"결혼식 정보 바로 보기"**를 뒀다.

> 이 버튼 하나가 나머지를 자유롭게 한다.
> 지름길이 있으니 탐험 쪽은 마음 놓고 재미있게 만들 수 있다.

# 7. 겪은 문제와 원리

## 7-1. 픽셀 아트 모드에서 한글이 뭉개졌다

### 원리 — 텍스처 확대와 필터링

GPU에 올라간 그림을 **텍스처**라고 한다. 텍스처를 원래 크기보다 크게 그리면
GPU는 **없는 픽셀을 만들어내야** 한다. 방식이 두 가지다.

```text
Linear (선형)    주변 픽셀을 섞는다        → 부드럽지만 흐릿
Nearest (최근접)  가장 가까운 픽셀을 복사   → 각지지만 선명
```

픽셀 아트는 **Nearest**를 쓴다. 그래야 픽셀이 뭉개지지 않는다.

### 무엇이 문제였나

Phaser의 Text는 글자를 **작은 그림으로 한 번 구운 뒤** 화면에 붙인다.
9px로 구운 그림을 카메라가 3배로 늘리는데, Nearest라서
**글자 픽셀 하나가 3×3 블록**이 된다.

알파벳은 획이 단순해서 버티지만, **한글은 9px 안에 담을 획이 없다.**
그래서 더 심하게 뭉갠다.

### 해결

`resolution: 3`을 주면 글자 그림을 **처음부터 3배 크기로 굽는다.**
카메라가 3배로 늘려도 텍스처 1픽셀 = 화면 1픽셀이 되어 또렷하다.

---

## 7-2. 모바일 화면 위쪽이 잘렸다

### 원리 — 모바일에는 화면 높이가 세 개 있다

모바일 브라우저는 스크롤하면 주소창이 숨는다. 그래서 "화면 높이"가 하나가 아니다.

```text
lvh (large)    주소창이 숨었을 때의 큰 높이
svh (small)    주소창이 보일 때의 작은 높이
dvh (dynamic)  지금 이 순간의 높이. 주소창이 움직이면 같이 변한다
```

`height: 100%`와 `100vh`는 전통적으로 **큰 높이(lvh)** 를 가리킨다.
그래서 주소창이 보이는 동안에는 **실제로 보이는 것보다 요소가 더 크다.**

가운데 정렬한 내용이 그 큰 상자의 한가운데에 놓이니,
**위쪽이 주소창 뒤로 밀려 잘렸다.**

### 왜 dvh가 아니라 svh인가

`dvh`는 주소창이 움직일 때마다 높이가 변한다.
그러면 **게임 캔버스가 계속 크기를 다시 계산**해서 화면이 출렁인다.

`svh`는 항상 가장 작은 높이라서 **절대 잘리지 않고 변하지도 않는다.**

## 7-3. flexbox 가운데 정렬의 함정 (같이 겪음)

### 원리

`justify-content: center`는 남는 공간을 위아래로 **똑같이 나눠준다.**
그런데 내용이 컨테이너보다 크면 남는 공간이 **음수**가 된다.
음수를 반씩 나누면 **위쪽이 컨테이너 밖으로 밀려난다.**

스크롤은 **시작 지점보다 위로는 올라가지 못한다.**
그래서 밀려난 부분에 영영 손이 닿지 않는다.

### 해결 — margin: auto

`margin: auto`는 **남는 공간이 있을 때만** 흡수한다.
공간이 부족하면 그냥 시작 지점에 붙는다. 그러면 정상적으로 스크롤된다.

```text
justify-center   넘치면 위쪽이 잘리고 못 본다
my-auto          넘치면 스크롤된다
```

## 7-4. 애니메이션 라이브러리가 좌표를 붙잡고 있었다

안내 표시(▼)를 tween으로 위아래로 흔들었다.
동시에 매 프레임 오브젝트 머리 위로 위치를 옮겼다.

**tween이 y값을 소유하고 있어서 내가 옮긴 위치를 매 프레임 덮어썼다.**
표시가 오브젝트 위가 아니라 맵 구석에 붙어 있었다.

tween을 걷어내고 `update()`에서 사인 곡선으로 직접 계산했다.

> **라이브러리가 어떤 상태를 소유하는지 확인하지 않으면 충돌이 난다.**
> 같은 값을 두 곳에서 쓰지 않는다는 일반 원칙의 예다.

---

## 7-5. 복사·공유가 폰에서만 안 됐다

### 원리 — 보안 컨텍스트(Secure Context)

브라우저는 위험한 기능을 **https 또는 localhost에서만** 허용한다.
클립보드, 위치정보, 카메라, 공유 API가 그렇다.

**왜 그런가** — 평문 http는 중간에서 누구든 내용을 바꿔치기할 수 있다.
공용 와이파이에서 스크립트를 끼워 넣어 **클립보드를 읽어가는 공격**이 가능해진다.
그래서 아예 API 자체를 없는 값으로 만든다.

### 이 프로젝트에서

폰에서 `http://192.168.x.x:3000`으로 테스트하니 `navigator.clipboard`가
아예 `undefined`였다. 옛날 방식(`execCommand`)을 대비책으로 넣어 복사는 되게 했다.

배포하면 https라 첫 번째 방법이 쓰인다.

---

## 7-6. 폰에서 개발 서버 접속이 안 됐다 — 원인 세 개

### (1) IP가 바뀌어 있었다

공유기는 IP를 **빌려준다(DHCP).** 기간이 끝나거나 재접속하면 다른 번호를 받는다.
어제 쓰던 주소가 오늘은 다른 기기 것일 수 있다.

### (2) 개발 서버가 알려주는 주소를 믿을 수 없었다

Next는 루프백이 아닌 네트워크 어댑터 중 **하나를 골라** 보여준다.
이 PC에는 WSL 가상 어댑터가 있어서 그쪽 주소를 고르기도 했다.
**가상 어댑터 주소는 폰에서 절대 닿지 않는다.**

### (3) Next.js 16이 교차 출처 요청을 막고 있었다

**왜 막는가** — 개발 서버는 소스맵과 HMR 통로를 열어둔다.
아무 웹사이트나 그걸 가져갈 수 있으면 **내 소스코드가 새어나간다.**
그래서 `/_next/*` 요청의 출처를 확인한다.

증상이 헷갈린다. HTML은 오는데 **스크립트만 403으로 막혀 화면이 깨진다.**
`allowedDevOrigins`에 사설 IP 대역을 허용해 해결했다.

> **하나씩 배제해 나간 과정**을 설명하면 디버깅 방식을 보여줄 수 있다.
> 서버가 듣고 있는지 → 방화벽 → 주소가 맞는지 → 애플리케이션 레벨 차단.

---

## 7-7. CSS 우선순위 — 레이어

### 원리 — 캐스케이드 레이어는 명시도보다 먼저 본다

CSS는 보통 **명시도**(선택자가 얼마나 구체적인가)로 승부를 가른다.
그런데 **캐스케이드 레이어**(`@layer`)가 있으면 그보다 먼저 레이어를 본다.

**레이어에 들어간 스타일은 레이어 밖 스타일보다 항상 약하다.**
명시도와 무관하다.

Tailwind 4는 유틸리티를 레이어 안에 넣는다.
그래서 `create-next-app`이 넣어둔 **평범한 `body { background: ... }`가
`bg-[#0f0f1b]` 유틸리티를 이긴다.**

흰 배경이 계속 나오던 이유였다.

### 같이 발견한 것

**쓰지도 않는 웹폰트 두 벌이 다운로드되고 있었다.**
한글 글리프도 없어서 어차피 대체 폰트로 넘어가는 것들이었다.
모바일에서 불필요한 폰트 다운로드는 그대로 로딩 시간이다. 걷어냈다.

---

## 7-8. npm이 엉뚱한 곳에 설치했다

### 원리 — npm은 위로 거슬러 올라간다

`npm install`은 현재 디렉터리에 `package.json`이 없으면
**상위 폴더로 계속 올라가며 찾는다.**

터미널 위치가 `node_modules/next/dist/docs` 인 상태에서 실행했더니
`node_modules/next/package.json`을 발견하고 **next 패키지 안에 설치**해 버렸다.

### 복구 — install과 ci의 차이

```text
npm install   package.json을 보고 설치. 버전 범위 안에서 최신을 가져올 수 있다
              package.json / lockfile을 수정한다

npm ci        lockfile만 보고 설치. 기록된 정확한 버전 그대로
              node_modules를 통째로 지우고 새로 만든다. package.json을 안 건드린다
```

`ci`는 Clean Install이다. **환경을 정확히 복원할 때** 쓴다.
CI 서버에서 쓰는 이유이기도 하다 — 빌드할 때마다 같은 버전이 보장돼야 하니까.

`npm ci`로 전체를 복원한 뒤 올바른 위치에서 다시 설치했다.

# 8. AI를 어떻게 썼나

**요즘 반드시 나오는 질문이다. 준비해두면 차별점이 된다.**

## 핵심 — 검증할 수 있는 것만 믿었다

```text
AI가 쓴 코드      →  tsc / lint / 프로덕션 빌드로 거른다
AI가 만든 데이터  →  검증 스크립트를 따로 짜서 거른다
화면              →  내가 직접 본다
```

맵 데이터는 눈으로 못 믿어서 **BFS 도달성 검사 스크립트**를 짰다.
갈 수 없는 칸 8개를 그렇게 찾았다.

## 라이브러리 버전 함정

Phaser는 4.x인데 **인터넷 예제와 학습 데이터 대부분이 3.x**다.
그대로 쓰면 조용히 동작하지 않거나 미묘하게 다르게 동작한다.

그래서 `node_modules/phaser/skills/`에 들어 있는
**설치된 버전의 공식 문서**를 직접 읽고 작업했다.
Next.js도 `node_modules/next/dist/docs/`를 봤다.

> **기억이 아니라 설치된 것을 확인한다.**
> AI를 쓸 때 가장 자주 깨지는 지점이 버전 차이다.

## 오래된 에러 로그에 속을 뻔했다

파일 두 개를 순서대로 고치는 사이,
개발 서버가 중간 상태에서 "export가 없다"는 에러를 잔뜩 뱉었다.

**콘솔에 남아 있던 과거 로그**였다. 현재 코드는 멀쩡했다.
프로덕션 빌드를 돌려 확인했다.

> 로그의 **시점**을 확인하지 않으면 없는 버그를 쫓게 된다.

## 문서 구조를 AI 협업에 맞게 다시 짰다

처음에는 기획·진행상황·학습노트가 **한 파일 1,950줄**이었다.
세션마다 전부 읽느라 **실제 작업보다 부대비용이 컸다.**

역할별로 쪼갰다.

```text
CLAUDE.md          세션마다 자동으로 읽힘. 규약과 판단 기준만
docs/STATUS.md     현재 상태와 다음 작업. 100줄 이내로 유지
docs/BACKLOG.md    미룬 것 + 왜 미뤘는지 + 언제 다시 볼지
docs/BLUEPRINT.md  기획. 방향이 바뀔 때만
docs/notes/        개념 정리. 해당 주제를 건드릴 때만
```

**매 세션 읽는 양이 1,950줄에서 약 90줄로 줄었다.**

규칙도 하나 세웠다. **같은 내용을 여러 곳에 쓰지 않는다.**

```text
"이 줄이 왜 이런가"   → 코드 주석
"지금 어디까지 왔나"  → STATUS.md
"개념이 무엇인가"     → notes/
"무슨 일이 있었나"    → git log
```

> 이 이야기가 의외로 강하다. **AI를 쓰는 것 자체는 이제 특별하지 않다.
> 어떻게 쓸지를 설계했느냐**가 차이다.

# 9. 아쉬운 점 (반드시 물어본다)

솔직하게 말하고, **왜 그렇게 뒀는지**를 함께 말한다.

```text
테스트가 없다      A* 같은 순수 함수는 테스트하기 좋은데 아직 안 짰다
서버가 없다        전부 정적이다. 방명록을 넣으면 그때 필요해진다
CI가 없다          혼자 하는 프로젝트라 미뤘다
코드 리뷰가 없다    혼자라 놓친 것이 있을 수 있다
그래픽이 임시다     코드로 그린 색 사각형이다
```

## 임시 그래픽은 의도적이다

그림을 기다리면 개발이 멈춘다. 그래서 **코드로 그린 임시 그래픽으로 먼저 만들고,
교체 지점을 파일 두 개로 좁혀 뒀다.**

캐릭터 4방향도 그림보다 코드를 먼저 만들었다.
방향을 기억하고 애니메이션을 갈아끼우는 구조를 완성해두면
진짜 그림이 왔을 때 **그리는 함수만 이미지 로딩으로 바꾸면 된다.**

> **의존성을 끊어 병렬로 갈 수 있게 만든 판단**으로 설명한다.

## 4방향은 9장이면 된다

12장이 아니다. **왼쪽은 옆모습을 좌우로 뒤집어 쓴다.**

```text
앞모습 3장 + 뒷모습 3장 + 옆모습 3장 = 9장
```

포켓몬 같은 고전 픽셀 RPG가 쓰는 방식이다. 그림 양이 25% 줄었다.

# 10. 예상 질문과 답변

## 왜 이 프로젝트를 했나

실제로 쓸 물건이 필요했고, 동시에 React·Next.js·Phaser를 제대로 써보고 싶었다.
**튜토리얼보다 마감과 실제 사용자가 있는 물건이 훨씬 많이 남는다.**

## 게임 개발을 하고 싶은 건가

아니다. 게임은 **콘텐츠를 탐색하는 인터페이스**로 쓴 것이다. 전투도 레벨도 없다.
배운 것은 게임 개발이라기보다 **성격이 다른 두 렌더링 시스템을
한 화면에서 공존시키는 방법**이다.

## 혼자 다 했나 / AI를 얼마나 썼나

적극적으로 썼고, 대신 **검증을 설계했다.** (§8)
숨길 것이 아니라 **어떻게 썼는지**를 말한다.

## 성능은 어떻게 고려했나

- 그림을 매번 그리지 않고 **텍스처로 한 번 구워** 재사용한다
- 고양이 따라다니기에 길찾기를 쓰지 않는다 (§5-2)
- 전부 정적 생성이라 서버가 없다
- 쓰지 않는 웹폰트 두 벌을 제거했다
- 타일맵은 화면에 보이는 타일만 그린다 (Phaser가 처리)

## 정적 생성이 뭔가 / SSR과 뭐가 다른가

```text
CSR    브라우저가 빈 HTML을 받고 JS로 화면을 만든다. 크롤러가 못 읽는다
SSR    요청이 올 때마다 서버가 HTML을 만든다. 서버가 계속 돌아야 한다
SSG    빌드할 때 HTML 파일을 미리 만들어 둔다. 파일 서버만 있으면 된다
```

이 프로젝트는 전부 **SSG**다. 내용이 사람마다 다르지 않으니 미리 만들어도 된다.
그래서 **서버 비용이 0**이고, 어느 정적 호스팅에나 올릴 수 있다.

방명록을 넣으면 사람마다 내용이 달라지므로 그때 서버가 필요해진다.

## 확장한다면

청첩장은 **첫 사용 사례**다. 구조적으로는 "나만의 2D 추억 공간"으로 넓힐 수 있다.
지금 데이터 폴더만 갈아끼우면 다른 이야기가 된다.

## 다음에 뭘 할 건가

배포 → README 정비 → 방명록(서버·DB) → 테스트.
방명록이 **처음으로 서버가 꼭 필요해지는 지점**이다.

# 11. 배포 — 원리부터

## 11-1. 배포란 무엇인가

지금 이 프로젝트는 **내 노트북 안에서만** 돈다.
`npm run dev`를 하면 내 컴퓨터가 잠깐 서버 역할을 하는 것이다.
노트북을 닫으면 사라진다.

**배포는 "항상 켜져 있고, 누구나 주소로 찾아올 수 있는 컴퓨터에
결과물을 올려두는 일"이다.** 그게 전부다.

### 왜 지금 주소로는 밖에서 못 들어오나 — 사설 IP

폰으로 테스트할 때 `172.24.236.209` 같은 주소를 썼다.
이건 **사설 IP**다. 밖에서는 이 주소로 길을 찾을 수 없다.

**왜 이런 게 있나** — IPv4 주소는 약 43억 개뿐이라 진작에 모자랐다.
그래서 집·회사 안에서는 아래 대역을 자기들끼리 쓰기로 약속했다.

```text
10.0.0.0     ~ 10.255.255.255
172.16.0.0   ~ 172.31.255.255
192.168.0.0  ~ 192.168.255.255
```

이 대역은 **인터넷 라우터가 아예 전달해주지 않는다.** 우리 집 `192.168.0.5`와
옆집 `192.168.0.5`가 동시에 존재하니 구분할 방법이 없기 때문이다.
공유기가 하나의 공인 IP를 여럿이 나눠 쓰게 중계(NAT)해줄 뿐이다.

> **배포가 필요한 근본 이유가 여기 있다.** 공인 IP를 가진 컴퓨터가 필요하다.

## 11-2. 빌드가 하는 일

### 개발 서버와 무엇이 다른가

```text
개발 서버   파일이 바뀔 때마다 그때그때 변환한다. 느리지만 편하다
빌드        한 번에 전부 변환하고 최적화한다. 결과물을 파일로 남긴다
```

빌드가 실제로 하는 일들이다.

```text
TypeScript → JavaScript      브라우저는 TS를 모른다
JSX → 함수 호출              <div>는 자바스크립트 문법이 아니다
번들링                       수백 개 파일을 몇 덩어리로 합친다
트리 셰이킹                   안 쓰는 코드를 잘라낸다
압축(minify)                 변수명을 줄이고 공백을 없앤다
코드 스플리팅                 첫 화면에 필요 없는 건 나중에 받게 쪼갠다
```

우리 프로젝트는 여기에 더해 **HTML 파일까지 미리 만든다**(정적 생성).

### 파일 이름에 해시가 붙는 이유 — 캐시

빌드 결과를 보면 `chunk-a3f9b2.js` 처럼 **내용 해시**가 파일명에 들어 있다.

**왜 그러나** — 브라우저는 한 번 받은 파일을 캐시에 저장해두고 재사용한다.
그런데 파일명이 그대로면, 내가 코드를 고쳐도 **브라우저가 옛날 파일을 계속 쓴다.**

내용이 바뀌면 해시가 바뀌고, 해시가 바뀌면 파일명이 바뀐다.
브라우저 입장에서는 **처음 보는 파일**이니 새로 받는다.

덕분에 캐시를 아주 길게(1년) 걸어도 안전하다.
"내용이 바뀌면 이름이 바뀐다"가 보장되기 때문이다.

## 11-3. Git 연동 배포가 돌아가는 순서

Vercel 같은 서비스는 GitHub과 연결해두면 이렇게 동작한다.

```text
① git push
② GitHub이 Vercel에 "새 커밋이 있다"고 알린다 (webhook)
③ Vercel이 코드를 내려받아 npm install → npm run build
④ 빌드가 성공하면 결과물을 배포한다. 실패하면 이전 버전이 그대로 유지된다
⑤ 완료되면 URL이 갱신된다
```

**이것이 CI/CD의 가장 단순한 형태다.**
CI(지속적 통합)는 "합칠 때마다 자동으로 빌드·검증한다",
CD(지속적 배포)는 "통과하면 자동으로 내보낸다"는 뜻이다.

### 브랜치마다 미리보기 주소가 생긴다

`main`이 아닌 브랜치를 push하면 **그 브랜치만의 임시 URL**이 만들어진다.
실무에서 PR 리뷰할 때 "코드만 보지 말고 여기 들어가서 눌러보세요"가 가능해진다.

> 혼자 하는 프로젝트라도 이 구조를 아는 것과 모르는 것은 다르다.

## 11-4. CDN — 왜 파일을 여러 곳에 복사하나

### 원리 — 거리는 시간이다

서버가 미국에 하나만 있으면, 한국에서 접속할 때마다 신호가 **태평양을 왕복**한다.
빛의 속도는 정해져 있어서 이건 돈으로도 못 줄인다. 왕복에 150~200ms쯤 든다.

**CDN**은 같은 파일을 세계 여러 지점에 미리 복사해두고,
접속한 사람과 **가장 가까운 지점**이 응답하게 한다. 한국에서 접속하면
서울이나 도쿄 서버가 답한다. 10~30ms로 줄어든다.

### 왜 정적 사이트가 CDN과 궁합이 좋은가

정적 파일은 **누가 언제 요청해도 결과가 같다.** 그래서 아무 데나 복사해도 된다.

반면 사람마다 다른 내용을 만들어야 하면(로그인한 사용자 정보 등)
그 계산을 할 수 있는 서버가 필요해서 복사가 간단하지 않다.

> 이 프로젝트가 전부 정적이라는 사실이 **비용과 속도 양쪽에서 이득**이라는
> 설명으로 이어진다.

## 11-5. 도메인과 DNS

### 원리 — 이름을 번호로 바꾸는 전화번호부

사람은 이름을 기억하고 컴퓨터는 숫자(IP)로 통신한다. 그 사이를 잇는 게 **DNS**다.

브라우저에 주소를 치면 대략 이런 순서로 물어본다.

```text
브라우저 캐시 → OS 캐시 → 통신사 DNS 서버
   → 최상위(.com을 아는 곳) → 그 도메인을 실제로 관리하는 서버
```

답을 받으면 **TTL**(유효 시간) 동안 캐시한다.
도메인 설정을 바꿔도 바로 반영되지 않고 몇 시간 걸리는 이유가 이것이다.
세상 곳곳에 캐시된 옛 정보가 만료돼야 한다.

### 레코드 종류

```text
A 레코드      도메인 → IP 주소를 직접 지정
CNAME 레코드   도메인 → 다른 도메인을 가리킴
```

호스팅 업체는 보통 **CNAME**을 쓰라고 한다. 그래야 업체가 서버 IP를 바꿔도
사용자가 설정을 고칠 필요가 없다.

### 이 프로젝트에서는

`프로젝트명.vercel.app` 같은 하위 도메인은 공짜로 주어진다.
**포트폴리오용으로는 이걸로 충분하다.** 실제 청첩장으로 쓸 때만
`.com`(연 1~2만원)을 붙이면 된다.

## 11-6. HTTPS — 왜 자동으로 되는가

### 원리 — 암호화와 신원 증명, 두 가지

HTTPS는 두 가지를 한다.

```text
암호화     중간에서 내용을 훔쳐보거나 바꿔치기하지 못하게 한다
신원 증명   "이 서버가 정말 그 도메인의 주인이 맞다"를 보증한다
```

두 번째가 **인증서**다. 신뢰받는 기관이 "이 도메인의 주인이 맞다"고 서명해준다.
서명이 없으면 브라우저가 경고를 띄운다.

예전에는 인증서가 유료였는데, **Let's Encrypt**가 무료 자동 발급을 시작하면서
호스팅 업체들이 이걸 자동화했다. 그래서 요즘은 배포하면 그냥 https가 된다.

### 이 프로젝트에서 왜 중요한가

§7-5에서 본 것처럼 **클립보드와 공유 API는 https에서만 동작한다.**
지금 폰 테스트에서 반쪽만 동작하던 것이 배포하면 정상이 된다.

카카오톡 미리보기도 https여야 제대로 읽힌다.

## 11-7. 환경변수 — NEXT_PUBLIC_ 접두사의 의미

### 원리 — 브라우저로 나가는 값과 서버에만 남는 값

환경변수는 코드에 박지 않고 밖에서 주입하는 값이다.
서버 주소나 API 키처럼 **환경마다 달라지거나 숨겨야 하는 것**에 쓴다.

Next.js에는 규칙이 하나 있다.

```text
NEXT_PUBLIC_ 이 붙은 것      빌드할 때 코드 안에 문자열로 박힌다 → 브라우저에서 보인다
붙지 않은 것                 서버에서만 읽힌다 → 브라우저로 나가지 않는다
```

**중요한 함의 두 가지다.**

첫째, `NEXT_PUBLIC_`에 **비밀을 넣으면 안 된다.** 개발자 도구로 다 보인다.

둘째, 이 값은 **빌드 시점에 박히므로** 나중에 바꾸려면 다시 빌드해야 한다.
서버를 재시작한다고 바뀌지 않는다.

### 이 프로젝트에서는

`NEXT_PUBLIC_SITE_URL`에 배포 주소를 넣는다.
카카오톡 미리보기 이미지의 **절대 경로**를 만드는 데 쓰인다.
크롤러는 `/opengraph-image` 같은 상대 경로를 이해하지 못하므로
`https://내주소/opengraph-image` 형태여야 한다.

비밀이 아니고 브라우저에서 보여도 되는 값이라 `NEXT_PUBLIC_`이 맞다.
