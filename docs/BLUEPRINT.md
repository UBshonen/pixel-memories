# 1. 프로젝트 개요

## 프로젝트명

**Pixel Memories**

## 한 줄 정의

> **추억을 탐험하는 픽셀 RPG형 모바일 청첩장**

기존 모바일 청첩장처럼 사진과 텍스트를 위에서 아래로 읽는 것이 아니라, 하객이 작은 픽셀 공간을 직접 돌아다니며 신랑·신부의 추억과 결혼식 정보를 발견하는 서비스다.

---

# 2. 해결하려는 문제

현재 모바일 청첩장은 대부분 비슷한 구조를 가진다.

```text
메인 사진 → 인사말 → 신랑/신부 소개 → 사진 → 예식 정보 → 지도 → 계좌번호
```

디자인은 달라도 사용자 경험은 대부분 **스크롤해서 정보를 읽는 것**에 머문다.

Pixel Memories는 이를 바꾼다.

```text
읽는 청첩장  →  탐험하는 청첩장
```

---

# 3. 핵심 경험

하객은 청첩장을 읽는 것이 아니라 **작은 추억의 공간에 초대된다.**

```text
              [결혼식장]
                   │
        [사진관] ─ 광장 ─ [카페]
                   │
              [추억의 집]
                   │
                [정원]
```

각 장소에 신랑·신부의 기억이 배치된다.

```text
사진 액자    → 실제 사진 보기
NPC          → 해당 시기의 이야기
게시판       → 방명록
앨범         → 사진 모음
결혼식장     → 날짜 / 시간 / 장소
버스 정류장  → 오시는 길
우체통       → 축하 메시지
```

핵심 경험은 다음 순환이다.

> **이동 → 발견 → 상호작용 → 추억 확인**

# 4. 디자인 원칙

## 4.0 이 서비스가 지켜야 할 네 가지

기능을 더하거나 뺄 때 이 네 가지로 판단한다. **넷 중 하나라도 무너지면 넣지 않는다.**

### 신기함

> "청첩장을 이렇게도 만드는구나"

첫인상이자 이 프로젝트의 존재 이유다. 이게 없으면 그냥 또 하나의 청첩장이다.
받은 사람이 남에게 보여주고 싶어지는 힘이 여기서 나온다.

### 귀여움

> 따라다니는 고양이, 꽃밭의 나비, 픽셀 캐릭터

정보만 있으면 한 번 보고 닫는다. 계속 보게 만드는 것은 귀여움이다.
기능이 없어도 귀여우면 값을 한다. 나비가 그렇다.

### 편의성

> 어르신이 학습 없이 쓸 수 있는가

**배워야 하면 실패다.** 하객의 상당수는 게임을 해본 적이 없는 분들이다.
"이걸 누르면 되는구나"를 스스로 알아내야 하는 장치는 그 자체로 피로다.

판단 기준:

```text
좋음   가만히 있어도 알려준다      움직이는 오브젝트, 먼저 말 거는 NPC, 길잡이 동물
나쁨   알아내야 알 수 있다         "이게 표지판이구나" 하고 눌러봐야 하는 것
```

### 전달성

> 날짜·장소·계좌가 확실히 닿는가

탐험이 즐거워도 정보가 안 닿으면 청첩장으로서 실패다.
**탐험하지 않고도 정보에 닿는 길**이 반드시 하나는 있어야 한다.

---

## 4.1 게임이 아니라 경험형 웹이다

본격적인 RPG를 만드는 프로젝트가 아니다. 게임 요소는 **콘텐츠를 탐색하기 위한 인터페이스**다.

따라서 전투·레벨·아이템 파밍·퀘스트 시스템은 핵심 범위가 아니다.

```text
걷는다 → 발견한다 → 누른다 → 추억을 본다
```

## 4.2 모바일 우선

하객은 대부분 카카오톡 링크를 통해 스마트폰으로 접속한다.

> **Mobile Web First**

앱 설치를 요구하지 않는다.

```text
카카오톡 링크 → 브라우저 → Pixel Memories 입장
```

## 4.3 진입 장벽은 매우 낮아야 한다

게임에 익숙하지 않은 사용자도 사용할 수 있어야 한다. 복잡한 조작법을 요구하지 않는다.

```text
화면 터치     → 캐릭터 해당 위치로 이동
가상 조이스틱 → 캐릭터 이동
```

최종 조작 방식은 모바일 UX 테스트 후 결정한다.

# 5. 사용자 유형

## 5.1 제작자 (신랑 / 신부)

자신의 Pixel Memories 공간을 만든다. 향후 서비스화할 경우 제작 과정은 최대한 쉬워야 한다.

```text
테마 선택 → 신랑/신부 정보 → 결혼식 정보 → 사진 업로드
→ 사진별 설명 → 배치할 장소 선택 → 미리보기 → 링크 생성
```

### 서비스화한다면 — 커플의 작업 시간을 15분 안에 묶는다

**진짜 질문은 "편집 기능을 넣느냐"가 아니라 "커플이 몇 분 쓰게 하느냐"다.**

한국 결혼 준비에서 청첩장은 스드메·예식장·상견례에 비하면 작은 항목이다.
기존 서비스는 10~20분이면 끝난다. 그 시기 커플에게 가장 부족한 것은 시간이고,
그다음이 결정할 기력이다.

여기에 "마을 어디에 액자를 놓으시겠어요?"를 묻는 것은 선물이 아니라 일감이다.
텍스트 입력은 노동이지만 배치는 **창작**이고, 창작은 잘하고 싶은 마음이 들어
훨씬 오래 걸린다.

**그래서 자유도를 주는 것이 아니라 뺏는다.**

```text
커플이 하는 일     사진 올리기 · 사진마다 한 줄 · 기본 정보
서비스가 하는 일   맵 배치 · 동선 · NPC 위치 · 연출
```

사진 6장을 올리면 시스템이 알아서 마을 곳곳에 배치한다.
배치 커스터마이징은 **원하는 사람만 여는 숨은 옵션**이지 필수 관문이 아니다.

### 만드는 순서

```text
1단계  직접 만들어 준다 (편집기 없음)
2단계  입력 폼 (사진 + 한 줄 + 기본 정보), 배치는 자동
3단계  배치 커스터마이징 — 숨은 옵션
```

1단계를 건너뛰지 않는다. 이유는 셋이다.

- 사용자가 열 명일 때 편집기를 만드는 것은 낭비다. 직접 만드는 편이 빠르다
- **수작업 10건이 곧 요구사항 명세서다.** 커플이 실제로 무엇을 보내오고
  어디서 막히는지 모르는 상태에서 만든 편집기는 십중팔구 틀린다
- 수작업이 병목이 되는 순간이 곧 수요가 검증된 순간이다. 그때 만들어도 늦지 않다

## 5.2 방문자 (하객 / 친구 / 가족)

별도 회원가입 없이 링크로 접근한다.

```text

→ 결혼식 정보 확인 → 방명록 / 사진 남기기
```

# 6. 방문자 시나리오

카카오톡으로 링크를 받는다.

```text
"저희 결혼합니다 💍"
[Pixel Memories 입장하기]
```

시작 화면이 나타난다.

```text
┌────────────────────────┐
│                        │
│     MINA ♥ JUNHO       │
│                        │
│   우리의 추억 마을에    │
│     초대합니다.         │
│                        │
│       [입장하기]        │
│                        │
└────────────────────────┘
```

입장하면 픽셀 공간이 나타나고, 캐릭터를 움직여 사진 액자로 이동한다. 상호작용하면 React UI가 열린다.

```text
┌─────────────────────────┐
│                         │
│        실제 사진         │
│                         │
│   "처음 제주 여행을      │
│    갔던 날"             │
│                         │
│        2022.05          │
│                         │
└─────────────────────────┘
```

다시 맵으로 돌아가 다른 추억을 탐험한다.

# 7. 콘텐츠 유형

| 유형 | 오브젝트 | 상호작용 결과 |
|---|---|---|
| 사진 | 액자, 앨범, 사진관, 폴라로이드 | 실제 사진 + 설명 |

| 게시판 | 게시판, 우체통 | 방명록, 축하 메시지 |

| 교통 | 버스 정류장, 자동차, 표지판 | 지도, 주소, 대중교통, 주차 |

# 8. 실사진과 픽셀 그래픽의 이질감

픽셀 공간에 실제 사진을 그대로 표시하면 시각적 이질감이 생긴다.

```text
방법 A — 픽셀 프레임   실사진 유지, 픽셀 UI 프레임 안에서 표시
방법 B — 사진 필터     색감·질감을 공간 테마와 맞춤
방법 C — 도트 변환     사진을 픽셀 아트로 변환 (원본도 볼 수 있게)
```

## 현재 방향

MVP에서는 **원본 사진 + 픽셀 스타일 프레임**(방법 A)부터 테스트한다.

AI 도트 변환은 후순위다.

---

# 9. 애니메이션

정적인 화면만 있으면 단순한 픽셀 테마 웹페이지처럼 느껴진다.

```text
캐릭터 걷기 / NPC idle / 나무 흔들림 / 물결 / 불빛 / 파티클
```

MVP에서는 **플레이어 이동 애니메이션**부터 구현한다.

# 10. MVP 정의

MVP의 목적은 다음을 검증하는 것이다.

> **이 컨셉이 실제 모바일 웹에서 재미있는가?**

처음부터 청첩장 제작 플랫폼 전체를 만들지 않는다.

| 단계 | 목표 | 내용 |
|---|---|---|
| MVP 1 | 탐험 가능 여부 | 맵, 플레이어, 이동, 카메라, 모바일 대응 |
| MVP 2 | 추억 탐색 | 상호작용 오브젝트, 사진 모달, 사진 설명, NPC 대화 |
| MVP 3 | 청첩장 기능 | 신랑/신부 소개, 예식 날짜·장소, 지도, 연락처 |
| MVP 4 | 참여 기능 | 방명록, 축하 메시지, 하객 사진 업로드 |

MVP 3까지 가면 **실제로 사용할 수 있는 RPG형 모바일 청첩장**이 된다.

---

# 11. MVP 이후 확장 아이디어

청첩장을 첫 사용 사례로 삼되 구조적으로는 더 확장할 수 있다.

```text
Pixel Memories
      ├─ Wedding
      ├─ Couple Memory
      ├─ Birthday
      ├─ Travel Memory
      └─ Personal Minihome
```

장기적으로는 **나만의 2D 추억 공간**이라는 방향으로 확장 가능하다. 과거 미니홈피의 감성과 공간형 인터페이스를 결합한 형태도 고려한다.

**현재 개발에서는 구현하지 않는다.**

## 남은 계획

순서대로 적었지만, 단계 2·3·4는 서로 독립적이라 병행할 수 있다.
**단계 1만은 반드시 먼저 끝내야 한다.**

### 단계 1 — 확정 (그림 작업을 막고 있는 것들)

지금 정하지 않으면 나중에 그린 그림을 버려야 하는 것들이다.

```text
[ ] 조작 방식      탭 이동만 vs 방향 버튼 병행
[ ] 카메라 배율     현재 3배
[ ] 타일 크기      현재 16px. 배율과 함께 판단
[ ] 캐릭터 방향 수  정면 1방향(현재) vs 4방향 → 그림 양이 4배 차이
[ ] 화면 비율 대응  기기별 세로 길이 차이
```

여기서 나오는 결론이 곧 **그림 발주서**가 된다.

### 단계 2 — 그래픽

이 프로젝트의 인상을 결정하는 단계다. 지금은 전부 코드로 그린 임시 그림이다.

```text
[ ] 타일 6종        잔디 · 꽃밭 · 길 · 물 · 나무 · 울타리
[ ] 캐릭터          단계 1의 방향 수에 따라 3~12프레임
[ ] 주민 2종 · 액자 · 예식장
[ ] UI 스타일       모달 테두리 · 버튼 · 글꼴
[ ] 약도
[ ] 사진 표현 방식   실사진과 픽셀의 이질감 (§8)
```

교체 지점은 `game/tiles.ts`와 `game/textures/placeholderTextures.ts` 두 파일뿐이다.

### 단계 3 — 청첩장으로서 빠진 것

기능 검증에 집중하느라 미뤄둔, **한국 모바일 청첩장에서 사실상 필수인 것들**이다.

```text
[ ] 카카오톡 공유 미리보기   링크를 보냈을 때 뜨는 썸네일과 문구 (OG 태그)
                             청첩장은 카톡으로 전달된다. 첫인상이 여기서 결정된다
[ ] 마음 전하실 곳           계좌번호. 복사 버튼 필요
[ ] 혼주 정보                양가 부모님 성함
[ ] 공유하기 버튼            받은 사람이 다시 전달할 수 있게
[ ] 시작 화면                "입장하기" (§6)
[ ] 로딩 화면                사진이 늘어나면 필요해진다
```

`카카오톡 공유 미리보기`는 서버 기능이 아니라 메타 태그라 지금도 만들 수 있지만,
**실제 확인은 배포 후에만 가능하다.**

### 단계 4 — 실제 내용

```text
[ ] 신랑·신부 정보, 예식 정보
[ ] 실제 사진과 설명
[ ] NPC 대사
[ ] 추억 개수에 맞춰 맵 구성 조정
```

전부 `data/` 폴더의 파일만 바꾸면 된다. 게임 코드는 손대지 않는다.

### 단계 5 — 참여 기능 (선택)

**여기서 처음으로 서버가 꼭 필요해진다.** 백엔드·DB·이미지 저장소를 이때 정한다.

```text
[ ] 방명록
[ ] 참석 여부 회신 (RSVP)
[ ] 하객 사진 업로드
```

# 14. React와 Phaser의 역할 분담

## Phaser — 게임 공간

```text
맵 / 캐릭터 / 이동 / 충돌 / NPC / 오브젝트 / 카메라 / 애니메이션
```

## React·Next.js — 웹 UI

```text
사진 모달 / 결혼식 정보 / 방명록 / 설정 / 제작 화면 / 로그인 / 폼
```

## 연결 방식

```text
Phaser: 캐릭터가 액자에 접근
            ↓
        상호작용 발생
            ↓
      React에게 이벤트 전달
            ↓
React:  사진 모달 표시
```

**모든 UI를 Phaser 안에서 구현하지 않는다.**

구현 세부는 [notes/react-phaser.md](notes/react-phaser.md) 참고.

# 17. 개발 원칙

## 원칙 1 — 작동하는 작은 결과부터 만든다

회원가입·관리자·DB·방명록·업로드를 처음부터 전부 만들지 않는다.

## 원칙 2 — 의미 있는 덩어리 단위로 완성하고 커밋한다

PHASE 하나마다 문서 갱신·커밋을 반복하면 의식이 작업보다 커진다. **눈에 보이는 결과가 나오는 단위**로 묶는다.

```text
예) "맵 위에서 캐릭터가 움직인다"        = PHASE 3~5 한 묶음
예) "액자를 누르면 사진 모달이 열린다"    = PHASE 7~8 한 묶음
```

## 원칙 3 — AI가 코딩하더라도 구조를 이해한다

목표는 AI 없이 모든 코드를 작성하는 것이 아니라, **AI가 작성한 코드라도 전체 구조와 실행 원리를 이해하는 것**이다.

## 원칙 4 — 과도한 선행학습을 하지 않는다

```text
필요한 기능 등장 → 관련 개념 학습 → 직접 구현 → 다음 기능
```

## 원칙 5 — 같은 내용을 여러 곳에 쓰지 않는다

```text
"이 줄이 왜 이런가"   → 코드 주석
"지금 어디까지 왔나"  → STATUS.md
"개념이 무엇인가"     → notes/
"무슨 일이 있었나"    → git log
```
